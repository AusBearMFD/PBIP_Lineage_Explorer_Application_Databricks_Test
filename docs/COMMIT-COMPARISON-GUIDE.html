Commit Comparison Guide

How PBIP Lineage Explorer reads a project's git history and works out what changed between versions of a Power BI report: which files it opens, the logic behind each tab, and exactly which version of your project it compares.

1. The short version

A PBIP project saves a Power BI report and its semantic model as ordinary text files. Git keeps a full copy of those files every time someone commits. The app reads those saved copies straight from the project's hidden .git folder, compares one version with the one before it, and translates the file differences back into Power BI terms: this measure's DAX changed, this relationship was made inactive, this visual lost a filter.

Changes tab

Looks only at the files each commit touched. Fast, and shows the raw before/after text of every changed file.

Compare tab

Rebuilds the whole project at each commit and compares it with the commit's parent. Sees deleted tables, page names, and anything still using something that was deleted.

Model tab, “Changes by commit”

Draws the semantic model before and after a commit, with new, deleted and edited tables and relationships marked.

Does it compare against GitHub or against my computer?

Against your computer's copy of the git history, starting from the commit you currently have checked out. The app never contacts GitHub. Commits you made locally but haven't pushed are included. Commits on GitHub that you haven't pulled are not. Edits you saved but haven't committed don't appear in the commit comparisons at all. They do appear in the lineage views and the Model tab's “Current model”, which read the files in your folder. Section 4 covers every case.

2. Power BI as text files

When a report is saved as a Power BI Project (.pbip) instead of a single .pbix file, Power BI Desktop writes a folder of small text files. Two folders matter:

Path inside the projectWhat it holdsFormat
Sales.SemanticModel/definition/tables/Sales.tmdlOne table: its columns (data type, source column, formula), its measures (DAX, format string, display folder), and its partitions (Power Query source and storage mode).TMDL
…/definition/relationships.tmdlEvery relationship: from and to columns, active or not, cross-filter direction, cardinality, security filter direction.TMDL
…/definition/roles/*.tmdlRow-level security roles and their DAX filters.TMDL
…/definition/expressions.tmdlShared Power Query queries and parameters.TMDL
Sales.Report/definition.pbirWhich semantic model this report is bound to (for example ../Sales.SemanticModel).JSON
…/definition/report.jsonReport-level settings and filters that apply to all pages, plus the theme.JSON
…/definition/pages/pages.jsonPage order and which page opens first.JSON
…/pages/pageId/page.jsonOne page: its display name, whether it's hidden, and its page-level filters.JSON
…/pages/pageId/visuals/visualId/visual.jsonOne visual: its type, the fields in each well, its title, visual-level filters, and a slicer's saved selection.JSON
…/definition/bookmarks/id.bookmark.jsonOne bookmark: target page, what's hidden or shown, the filter and slicer state it captured, and its Data / Display / Current page options.JSON
*/.pbi/ (for example cache.abf, localSettings.json)Local caches and per-user settings. Not part of the report's design, so the app skips them.mixed

IDs and display names

Pages, visuals and bookmarks are stored under an ID, a random-looking name such as 85f22ff15397e9ee0d93 that Power BI assigns once and never changes. The name you see in Power BI (“Sales Overview”, a visual's title) is stored inside the file. This matters for comparisons:

  • Renaming a page changes a value inside page.json. Its folder ID stays the same, so the app reports a rename, not a deletion plus a new page.
  • Two visuals with the same title are still told apart by their IDs.
  • Copying and pasting a visual gives the copy a new ID. The app can only infer that it's a copy, from a matching type, fields and title, so it marks it “Possible copy”.
  • A report folder copied to make a second report keeps the same page and visual IDs. That's why the app always compares each report folder separately.

What a field reference looks like

A visual doesn't store “Total Sales”. It stores which table and which field, and for columns, how they're aggregated:

// inside visual.json: a column in the Values well, summed
{ "Aggregation": { "Function": 0,
    "Expression": { "Column": { "Expression": { "SourceRef": { "Entity": "area_dashboard_crv_view" } },
                              "Property": "dta_area" } } } }

The app reads this as “Sum of area_dashboard_crv_view[dta_area]”. Entity is the table and Property the column or measure.

// inside relationships.tmdl
relationship 3f1c…
	fromColumn: area_dashboard_pemd.space_created_timestamp
	toColumn: date_dim.full_date
	isActive: false

Anything left out uses Power BI's default: active, single direction, many-to-one. The app fills in the defaults before comparing, so leaving a default out and writing it explicitly count as the same thing.

3. Git in six ideas

A commit is a full snapshot

Each commit records every file in the project as it was at that moment, plus a message, an author and a date. It is not just a list of edits.

Every commit has a parent

The parent is the commit it was built on. Comparing a commit with its parent shows what that commit changed. A merge commit has two parents.

Everything has an ID

Commits, folders and file contents are each identified by a hash, such as 83b05b8…. Identical file contents get identical IDs, so “did this file change?” is a quick ID comparison.

A branch is a pointer

A branch name (main, Dev_1.0) points to its latest commit. HEAD is the commit you currently have checked out.

Your clone is a full copy

The hidden .git folder in your project holds every commit you have downloaded. It's what the app reads.

Fetch, pull and push sync it

Fetch downloads new commits from GitHub. Pull fetches and moves your branch forward. Push uploads your commits. Nothing syncs on its own.

4. Your local copy vs what's on GitHub

There are three different versions of a project in play, and each feature of the app reads a specific one:

A, B and C exist in both places. The commit tabs only ever see what is in your clone.

SituationLineage views and Model “Current model”Changes, Compare and Model “Changes by commit”
You edited and saved in Power BI Desktop but didn't commitShownNot shown
You have unsaved edits open in Power BI DesktopNot shownNot shown
You committed but didn't pushShownShown (it's in your clone)

You ran git fetch but not git pullNot shownNot shown. The commits are downloaded, but your checked-out branch hasn't moved to them.

To review exactly what is on GitHub

Pull first (git pull, or Sync in GitHub Desktop or VS Code), make sure the branch you want is checked out, then open the folder in the app. If you have uncommitted work, commit or stash it so the files on disk match the commit being reviewed.

To review a branch that isn't yours yet, check it out (git checkout Dev/v2.1) and open the folder again.

One subtle mismatch

On the Changes tab, “impact” for an edited measure (which visuals show it) is traced through the project as it is on disk now, not as it was at that commit. On the Compare tab, dependency effects use the project as it was right after that commit. For an old commit, the two can name different visuals.

5. How the app reads git history

Everything runs in your browser. The app doesn't call GitHub, doesn't run the git program, and doesn't change anything in the repository.

  1. You pick the project folder

    Chrome and Edge let a web page read a folder you choose (the File System Access API). Pick the folder that contains the .git folder, the repository root. If you pick a sub-folder, the lineage views still work but the app reports “This folder is not a git repository”.

    src/parser/pbipReader.js · src/parser/gitFs.js (hasGitDirectory)

  2. A read-only adapter exposes .git

    A small adapter makes the chosen folder look like a normal file system to a git library. It only implements reading; there is nothing in it that writes.

    src/parser/gitFs.js (createGitFs)

  3. isomorphic-git reads the commits

    isomorphic-git is an open-source JavaScript implementation of git. It reads the commit list, folder listings and file contents from .git, including git's compressed “pack” files. The app keeps one shared cache so packs are unpacked only once.

    npm package isomorphic-git · buffer (a small helper it needs in the browser)

  4. Start at HEAD, newest first

    Both scans ask for the history of whatever is checked out (HEAD), newest first. The Changes tab reads 11 commits to make 10 pairs. The Compare tab reads 10 commits and compares each with its own parent.

    src/parser/gitScanner.js (scanGitHistory) · src/parser/snapshotScanner.js (scanVersionHistory)

  5. Only PBIP files

    Only .tmdl, .json and .pbir files are read. .pbi caches and node_modules folders are skipped.

The Changes scan starts on its own after a project loads, and its total appears on the Changes button. The Compare scan reads much more (every file of every version), so it starts the first time you open Compare or the Model tab's “Changes by commit”. On a repository with four reports and about 2,000 changed files in some commits, the Changes scan took about 11 seconds and the Compare scan about 15 to 30 seconds.

6. Changes tab (“Commit Edits”) pipeline

This tab answers: which PBIP files did each commit touch, and what does that mean in Power BI terms? It compares each commit with the next older commit in the list.

  1. Find the changed files

    The two commits' folder trees are compared from the top down. A folder whose ID is the same in both commits is identical, so it is skipped without being opened. That makes a commit that changed one visual quick, even in a large repository. Inside changed folders, a file counts as changed when its content ID differs.

    src/parser/gitScanner.js (getChangedFilesBetween)

  2. Read before and after text

    Each changed file's old and new contents are read by ID. A file that only exists on one side is new or deleted.

    src/parser/gitScanner.js (readBlobText)

  3. Split by report and model

    Files are grouped by their X.Report or X.SemanticModel folder and each group is compared on its own, so two reports that share IDs never get mixed up.

    packages/core/src/diff/changeDetector.js (detectChanges, pairByProject)

  4. Run one detector per kind of change

    Each detector parses its files and compares them field by field:

    • Pages: pages added or removed, default page, page filters. pageDiff.js
    • Report filters on all pages. filterDiff.js
    • Visuals: added or removed, hidden or shown, fields, visual filters, bookmark buttons. visualDiff.js
    • Bookmarks. bookmarkDiff.js
    • Measures, calculation items and columns. measureDiff.js
    • Relationships. relationshipDiff.js
    • Power Query sources, shared expressions and parameters. sourceDiff.js
    packages/core/src/diff/ · change types in changeTypes.js

  5. Trace the impact of measure changes

    For an edited, added or removed measure or calculation item, the app walks the current lineage graph to list the visuals that show it, including through field parameters and calculation groups.

    packages/core/src/diff/impactResolver.js

  6. Group by topic and show the text

    Changes are grouped into topics for the list, and each changed file gets a side-by-side line diff with unchanged stretches collapsed.

    packages/core/src/diff/changeTopics.js · textDiff.js · src/ui/changeHistoryView.js
Why this tab sometimes can't say more

It only sees the files a commit touched. If a commit deletes a table, it can't tell you that a visual (in a file the commit didn't touch) still uses that table. For that, and for page names on visuals whose page file didn't change, use the Compare tab.

7. Compare tab (Version Compare) pipeline

This tab answers: what does the project look like after this commit, compared with right before it?

  1. Pick each commit's real parent

    Each of the last 10 commits is compared with its first parent, even if that parent is further back in the list. A merge commit is compared with the branch it was merged into, so its changes are everything the merge brought in. The very first commit in a repository is compared with nothing, so everything in it is listed as new.

    src/parser/snapshotScanner.js (scanVersionHistory)

  2. Rebuild a full snapshot of both versions

    Every PBIP file in the commit is listed and read. Folder listings and file contents are cached by ID, and adjacent commits share almost all of them, so each is read only once across the whole scan.

    src/parser/snapshotScanner.js (listPbipFiles)

  3. Turn files into Power BI objects

    Files are grouped by X.SemanticModel and X.Report folder. For each model: tables, columns, measures, calculation items, partitions and sources, relationships, RLS roles and shared expressions. For each report: the bound model, theme, default page, report, page and visual filters, pages, visuals (type, title, fields, slicer selection) and bookmarks.

    packages/core/src/compare/snapshot.js (buildSnapshot) · reuses parser/tmdlParser.js

  4. Compare object by object

    Each object is matched with its counterpart by its identity, then property by property. The result is one record per difference, placed in Modified / Commit Edits (edited, renamed or deleted) or Additions (new).

    packages/core/src/compare/compareSnapshots.js (compareSnapshots)

  5. Work out dependency effects

    For an edited, deleted or renamed measure, column or table, the app indexes every DAX reference and every visual and filter in the after version, then follows the chain: measures that use it, measures that use those, calculated columns, field parameters, visuals, filters, RLS roles and relationships. Deleting or renaming something still in use breaks those things. Editing a formula only changes their values.

    packages/core/src/compare/dependencyImpact.js · DAX references from parser/daxParser.js

  6. Explain bookmarks

    For each bookmark, its captured state is compared with the target page's normal state: which objects it hides or shows, and which filters and slicers it changes. Settings that cancel parts of it are noted (for example Data not captured).

    packages/core/src/compare/bookmarkEffect.js

  7. Display

    Records are grouped by type, security-related and breaking changes are listed first, and they can be searched and filtered.

    src/ui/versionCompareView.js

How objects are matched between versions

ObjectMatched bySpecial handling
Report, semantic modelFolder pathA report's bound model comes from definition.pbir.
Table, columnNameA whole table that's new or deleted is one record that lists its columns and measures.
MeasureNameA deleted and a new measure with identical DAX are one rename. A measure moved to another table is not counted as breaking anything, because DAX finds measures by name.
RelationshipIts internal nameIf it was deleted and recreated with a new name but the same columns, it's matched by its columns.
Page, visual, bookmarkID (folder or file name)A visual's ID is combined with its page's ID. Titles are never used to match, so same-named visuals stay separate.
FilterIts internal nameA filter removed and re-added on the same field gets a new name, so it's matched by field and shown as one edit.
RLS roleNameAlways marked as a security change.

Only meaningful properties are compared. Bookkeeping that Power BI rewrites on every save (lineageTag, annotations, changedProperty) is ignored, as are visual formatting details other than the title text and hidden state. Whitespace differences in DAX and Power Query are ignored.

8. Model diagram, “Changes by commit”

The Model tab reuses the Compare scan. For the selected commit and semantic model it takes the before and after versions of the model and builds a combined diagram:

  • Tables and relationships in both versions are matched (relationships by name, then by columns), then tagged new, deleted, edited or unchanged.
  • Edited tables list their column changes (added, deleted, data type changed, formula edited) and a count of measure changes. Edited relationships list exactly what changed, such as “Active: Yes → No”.
  • Power BI's automatic date tables (LocalDateTable_…, one per date column when Auto date/time is on) are hidden by default, and their changes aren't counted.
  • The layout places each fact table at the centre of its dimension tables and keeps the same layout every time it's drawn.

packages/core/src/compare/modelDiagram.js (diffModelDiagram, layoutModelDiagram) · src/ui/modelDiagramView.js

9. A worked example

From the pbiws_area_dashboards repository: commit 83b05b8, “Merge pull request #22 from MFD-Eng/dev/v2.1”, the current state of its main branch.

  1. Find the parent

    It's a merge commit, so it's compared with its first parent, 2ade248, the state of main before the merge.

  2. Rebuild both versions

    All PBIP files of both commits are read: four reports and two semantic models.

  3. Compare the model

    In area_dashboard_crv_view.tmdl, the column dta_area exists before and is gone after, which produces a “Deleted column” record.

  4. Check what still uses it

    The after version's visuals are searched for Entity: area_dashboard_crv_view with Property: dta_area. One is found: the “Square Meters by Area” column chart (1991a1c) on the CRV page of Global Dashboard. That report's definition.pbir points to ../Area Dashboard.SemanticModel, so it is bound to the same model.

  5. Report it

    The record shows Breaks 1 visual and the card is flagged “Still referenced”. The commit's “Breaking changes” count goes up by one.

This was confirmed independently with git grep on that commit: that chart is the only visual referencing the deleted column.

11. Limits and tips

  • Last 10 commits only. To review older history, check out an older commit and open the folder again.
  • Merge commits differ between tabs. Compare uses the merge's first parent. The Changes tab compares neighbours in the commit list, which for a merge can be a commit from the other branch. The two tabs can therefore show different results for the same merge; Compare's is the one to trust.
  • Line endings. If a commit only converts line endings (Windows vs Mac/Linux), the Changes tab may count those files as changed, but no Power BI changes are listed for them. Compare reads the content, so it ignores them.
  • Shallow or partial clones. If the repository was cloned with limited history, older commits or parents may be missing, and those commits show as “could not be compared”.
  • Live-connected reports. A report bound to a published model (not a model folder in the repo) has no model to compare against, so dependency effects skip it.
  • DAX is read, not run. Dependency effects find references in the formula text. They don't evaluate DAX, so a reference built at run time (rare) isn't seen.
  • Browser. Chrome or Edge is required for folder access. The bundled sample project has no git history.

12. Glossary

PBIP
Power BI Project: a report and model saved as a folder of text files instead of one .pbix file.
TMDL
Tabular Model Definition Language, the text format for the semantic model (tables, measures, relationships, roles).
PBIR
The JSON format for the report (pages, visuals, bookmarks, filters).
Commit
A saved snapshot of the whole project in git, with a message, author and date.
Parent
The commit a commit was built on. Comparing with it shows what the commit changed.
Hash / ID
The unique code git gives each commit, folder and file content, such as 83b05b8 (shortened).
Branch
A named pointer to the latest commit on a line of work.
HEAD
The commit currently checked out in your folder. The commit scans start here.
Clone
Your local copy of a repository, including its .git folder.
Working copy
The files currently in your folder, including saved edits that aren't committed yet.
Fetch / pull / push
Download new commits / download and move your branch to them / upload your commits.
Merge commit
A commit that joins two branches; it has two parents.
Snapshot
In this app, a project fully rebuilt from one commit's files.
Dependency effects
Everything that still uses a changed or deleted object, and whether the change breaks it or only changes its values.
