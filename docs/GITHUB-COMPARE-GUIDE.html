GitHub Compare Guide

The app compares versions of a project from the local clone you open in the browser. This guide covers the second way to run the same comparison: straight from GitHub, without a clone, which is what mfd_utils.pbip_compare uses. It covers where that code lives, how it reuses the app, and how it is built and released.

1. The short version

All of the GitHub code is in one folder, integrations/github-compare/, plus one workflow file. It reads a PBIP repository through the GitHub API, runs the app's own compare engine on it, and writes a single HTML file with the app's Version Compare and Model Diagram views.

The app is unchanged

It still reads only your local folder and its .git history, in the browser. It never calls GitHub.

Nothing in the app was edited

The new folder only reads packages/core, two views in src/ui, and styles/main.css when it builds.

One engine, two front doors

A fix to the compare engine or those views shows up in both the app and the GitHub report.

3. Where the code is

integrations/github-compare/           all of the GitHub comparison code
├── src/sources/githubSource.js     reads commits and files from the GitHub API
├── src/refs.js                     picks the head and base branches
├── src/history.js                  builds "All changes" and the per-commit comparisons
├── src/payload.js                  what the report embeds (gzipped)
├── src/records.js                  flat rows for records.json
├── src/report/report.html, entry.js  the report page; mounts the two existing views
├── cli/pbip-compare.js             the command mfd_utils runs: arguments, exit codes, summary
├── build/build.mjs                 builds dist/pbip-compare.mjs (CLI + core + report in one file)
├── tests/                          14 offline tests using public/sample-pbip
└── README.md, package.json, package-lock.json, .gitignore
.github/workflows/pbip-compare-release.yml   builds, tests and publishes the release

The folder has its own package.json and lockfile, outside packages/, so it is not part of the root npm workspace: the root package-lock.json, npm run dev, npm run build and the root test suite (packages/core/tests) are all unaffected. dist/, node_modules/ and out/ inside it are ignored by git.

4. How it reuses the app

Solid line: used at run time. Dashed: bundled in when npm run build runs in the new folder. Neither side changes the shared files.

  • Compare engine: history.js calls the core's buildSnapshot and compareSnapshots, exactly as the app's src/parser/snapshotScanner.js does, so both produce the same records for the same two versions.
  • Views: the report page mounts versionCompareView.js and modelDiagramView.js through their existing init… / set… functions, the same way src/main.js does.
  • One copied piece: history.js repeats about 100 lines of the scanner's commit-pairing logic, because the original is tied to a browser folder handle and wasn't refactored.

5. What it compares

  1. Choose head

    An explicit --head or --pr; otherwise the newest open pull request; otherwise the most recently pushed branch other than the default branch. Otherwise it stops and asks for one.

    src/refs.js

  2. Choose base

    An explicit --base; otherwise the pull request's base branch; otherwise the repository's default branch.

    src/refs.js

  3. "All changes"

    The latest commit on base against the latest commit on head (tip to tip). If base has commits the branch doesn't, the report warns that some differences come from base.

    src/history.js

  4. Each branch commit

    Every commit on head that isn't on base, newest first, each against its first parent: the same rule the app uses. Up to --max-commits (default 30).

    src/history.js

The report header states which rule chose head, so an automatic choice is always visible.

6. How it reads GitHub

WhatGitHub API
Default branchGET /repos/{repo}
Newest open pull requestGET /repos/{repo}/pulls?state=open&sort=updated
Most recently pushed branchGET /repos/{repo}/activity?activity_type=push (falls back to branch tip dates)
Branch commits, and how far base is aheadGET /repos/{repo}/compare/{base}...{head}
PBIP files in a versionGET /repos/{repo}/git/trees/{sha}?recursive=1
File contentsGET /repos/{repo}/tarball/{sha} when more than 100 of a version's files aren't cached yet; GET /repos/{repo}/git/blobs/{sha} for the rest

It keeps the same files the app does: .tmdl, .json and .pbir, skipping .pbi/ and node_modules/, grouped by *.SemanticModel and *.Report folder. Files are cached by git blob id, so each file version downloads once however many commits contain it. On pbiws_area_dashboards (about 2,300 PBIP files), a one-commit pull request took 7 seconds and 70 requests; a 20-commit range took 32 seconds and 231 requests.

The report embeds the computed comparison, not the raw files, gzipped and base64-encoded, and the browser unpacks it with DecompressionStream. The pull request above made a 300 KB report.

7. How mfd_utils runs it

  1. Download the engine

    mfd_utils reads the pbip-compare-main-latest release of this repository, downloads pbip-compare.mjs when the release has a new build, checks it against pbip-compare.mjs.sha256, and caches it.

    mfd_utils: pbip_compare/tool.py

  2. Check the contract

    It runs node pbip-compare.mjs --version and refuses a build whose contract number it doesn't know.

    cli/pbip-compare.js · mfd_utils: pbip_compare/runner.py

  3. Run it

    It passes the repository and branch choices as arguments and the token as GITHUB_TOKEN, then reads the JSON summary on the last line of output, report.html and records.json.

    mfd_utils: pbip_compare/runner.py
# what a user types
from mfd_utils import pbip_compare
pbip_compare.compare("pbiws_area_dashboards", token=token)
# or
python -m mfd_utils.pbip_compare pbiws_area_dashboards --pr 23

# what mfd_utils runs
node pbip-compare.mjs --repo MFD-Eng/pbiws_area_dashboards --pr 23 --max-commits 30 --out <file>.html --json <file>_records.json

The contract

node pbip-compare.mjs --repo <owner/name> [--head <branch> | --pr <n>] [--base <ref>]
                      [--max-commits 30] [--out report.html] [--json records.json]
node pbip-compare.mjs --version        → {"version": "0.1.0", "commit": "…", "contract": 1}

env     GITHUB_TOKEN   never an argument, never written to output
stdout  last line: JSON summary (html, json, base, head, headReason, baseAheadBy, branchCommits,
        pairs, records, overall, warnings, githubRequests, seconds, htmlBytes)
exit    0 ok · 2 bad arguments · 3 auth · 4 not found / nothing to compare · 5 partial

9. Changing it safely

  • Changing the core or the two views changes the GitHub report too, on the next push to main. Run npm test in the folder as well as the root tests.
  • Raise contract in cli/pbip-compare.js only for breaking changes to the arguments, the summary or records.json, and update mfd_utils to match. Older mfd_utils versions will refuse the new build with a clear message instead of misreading it.
  • Bump version in the folder's package.json before running the workflow manually, so people can pin the release.
  • highlightDax is read from src/ui/lineageView.js at build time instead of bundling that whole file. If its DAX_FUNCTIONS, esc or highlightDax blocks are restructured, the build fails with a message naming build/build.mjs.

Known app bug found while building this

src/ui/lineageTree.js declares isVertical with const near line 517 and reassigns it near line 521, so the lineage tree throws a TypeError when source-first mode falls back. Vite builds it anyway; esbuild refuses it, which is why the report build avoids bundling lineageView.js. Changing const to let there fixes the app.

10. Limits

  • Only GitHub is supported as a source. A local-clone source for the command line is not built yet; the app remains the way to compare a local clone.
  • "All changes" is tip to tip, so when base has moved on, base's newer work also shows up. The per-commit entries show only the branch's own changes.
  • The views' own wording assumes one commit, so the "All changes" entry is labelled with "parent commit" and "this commit". The report header explains the comparison.
  • Each run counts against the token's 5,000 GitHub requests per hour.
  • Reports contain DAX, M and filter values from the repository. Share them like the repository itself.
Head
The branch being reviewed.
Base
The branch it's compared with, usually the pull request's target.
Tip
The latest commit on a branch.
Contract
The version number of the command-line interface mfd_utils relies on.
main-latest
The release rebuilt from every push to main.
